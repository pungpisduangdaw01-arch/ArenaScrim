# 03 — Scope Proposal (ฉบับร่าง)

> ⚠️ **เอกสารนี้เป็นข้อเสนอที่รอเจ้าของโครงการอนุมัติ ไม่ใช่ข้อกำหนดสุดท้าย**
> ทุกรายการเป็น **PROPOSAL** ห้ามเริ่มพัฒนาจนกว่าจะได้รับการอนุมัติเป็นรายข้อ
> ลำดับในแต่ละกลุ่มเรียงตามผลกระทบที่ประเมินไว้ ไม่ได้เรียงตามความนิยมของฟีเจอร์

## หลักการที่ใช้จัดกลุ่ม

1. คงสิ่งที่มีอยู่และตอบความต้องการ R1–R6 (ดู `02_GAP_ANALYSIS.md` §1)
2. ทำให้สิ่งที่มีอยู่ **ทำงานถูกต้องและพิสูจน์ได้** ก่อนเพิ่มของใหม่
3. ความสามารถใหม่ต้องมีหลักฐานว่าตอบช่องว่างจริง หรือต้องได้รับการยืนยันจากเจ้าของโครงการ
4. หลีกเลี่ยงการเพิ่มฟีเจอร์ที่ใช้ข้อมูลหรือโครงสร้างที่ยังไม่มี โดยเฉพาะฟีเจอร์ที่ต้องเปลี่ยน schema

## D. Not Included Unless Approved — ไม่ควรเริ่มโดยไม่มีการยืนยัน

ไม่พบหลักฐานในโค้ด บทความ หรือคำยืนยันจากเจ้าของโครงการว่ารายการเหล่านี้จำเป็น

| รายการ | เหตุผลที่ไม่รวม |
|---|---|
| ระบบจับคู่ทีมอัตโนมัติ (matchmaking) | ไม่มีหลักฐานความต้องการ และ lobby ปัจจุบันยังไม่มีการใช้งานจริง |
| แชตในระบบ | ทีมติดต่อผ่าน Discord/Line อยู่แล้ว (มีช่องทางในระบบ) |
| การแจ้งเตือน (อีเมล/push/in-app) | ต้องมีกลไกตอบรับก่อน (C-07/G-04) และต้องมีโครงสร้างพื้นฐานเพิ่ม |
| ตารางนัดซ้อม / ปฏิทิน / เช็กชื่อผู้เล่น | ไม่พบในบทความหรือโค้ด |
| ทัวร์นาเมนต์ / bracket | ไม่พบ |
| OCR อ่านค่าจากภาพหน้าจอ | บทความระบุเป็นงานในอนาคต มีความซับซ้อนสูง |
| วิเคราะห์ขั้นสูง / ML / การทำนายผล | ไม่พบ และข้อมูลยังมีน้อย |
| อัปโหลดไฟล์ภาพ | ระบบเลือกใช้ลิงก์แทนโดยตั้งใจ และการอัปโหลดเพิ่มความเสี่ยงด้านความปลอดภัย |
| ยืนยันอีเมล / รีเซ็ตรหัสผ่านทางอีเมล | ต้องมี mail server (ดู C-02) |
| Export CSV/Excel | ไม่มีหลักฐานความต้องการ |
| ย้ายไปใช้ framework / เขียนใหม่ | ขัดกับหลักแก้เฉพาะจุดและรักษาโครงสร้างเดิม |
